# v0.2.0 — Blue/Green Deployment Safety Controls

Status: release candidate. Publication has not been approved. This document is
the draft source for the GitHub Release notes.

## Release intent

`v0.2.0` expands the initial Docker Compose deployment template and Python CLI
into a broader deployment-control baseline. It adds deterministic policy checks
around promotion, evidence integrity, rollback readiness, migrations, and
recovery while retaining the Bash entry point for compatibility.

## Highlights

- Health-gated blue/green promotion now has explicit readiness, health-budget,
  quorum, soak, traffic-drain, and Nginx worker-drain contracts.
- Promotion state can be recorded, validated, resumed, and correlated through
  checkpoints and transition-journal evidence.
- Release inputs can be checked for immutable image identity, provenance,
  configuration fingerprints, platform compatibility, SBOMs, signatures, and
  rendered Compose provenance.
- Rollback controls cover artifact availability, command safety, data
  compatibility, recovery budgets, and observed execution evidence.
- Migration controls cover planning, expand-contract sequencing, compatibility,
  backup evidence, execution evidence, and rollback contracts.
- The unit suite exercises the deployment and policy behavior without requiring
  a live registry, production host, or privileged deployment in default CI.

See [`CHANGELOG.md`](../../CHANGELOG.md) for the categorized change list.

## Compatibility and upgrade notes

- Python 3.10 or newer remains required.
- `python3 -m compose_zero_downtime`, the installed
  `compose-zero-downtime` command, and `deploy/blue-green-deploy.sh` remain
  supported entry points.
- No persisted state or configuration migration is performed by this release.
- Existing users can adopt the new evidence policies incrementally; enabling a
  gate requires supplying reviewed evidence that matches the target
  environment and immutable release identity.
- The deployment model still requires stateless application instances,
  reliable health checks, externally managed persistent state, and backward-
  compatible database changes while both colors run concurrently.

## Known limitations

- The project validates deployment contracts and supplied evidence; it cannot
  prove that an external evidence collector or target host is trustworthy.
- The local demo does not reproduce production load balancers, orchestrators,
  registries, secret stores, or database failure modes.
- “Zero downtime” is conditional on the documented application, proxy,
  capacity, health-check, and migration assumptions.
- Default CI does not perform a privileged live deployment or destructive
  rollback drill.
- Secret scanning reports no open alerts. Dependabot and code-scanning alert
  feeds were unavailable during this release review.

## Release validation

Run from a clean checkout of the candidate commit:

```bash
python3 -m unittest discover -s tests
python3 -m compose_zero_downtime --help
bash -n deploy/blue-green-deploy.sh
docker compose -f deploy/docker-compose.blue-green.yml config >/dev/null
python3 .github/scripts/daily_pr.py --dry-run
python3 -m json.tool .github/daily-pr/backlog.json >/dev/null
git diff --check v0.1.0...HEAD
```

Expected results:

- all unit tests pass;
- the CLI exposes its deployment and recovery commands;
- the compatibility wrapper has valid shell syntax;
- the Compose model resolves successfully;
- completed automation backlog returns a successful no-op;
- backlog JSON parses successfully;
- the release diff contains no whitespace errors.

## Rollback

This release changes deployment tooling and validation policies but performs no
automatic data migration. If a downstream pipeline cannot adopt `v0.2.0`, pin
it to `v0.1.0` and restore the previous include reference. Preserve the active
color and its release artifacts while investigating; do not bypass a failed
promotion or rollback gate merely to complete the version rollback.
